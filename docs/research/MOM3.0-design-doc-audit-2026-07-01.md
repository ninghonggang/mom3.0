# MOM3.0 设计文档现状审计

**审计日期**: 2026-07-01
**审计范围**: `/data/mom3.0/docs/` 下所有 `MOM3.0_*.md` 设计文档
**审计方法**: 通读 + 与代码对照 + 与同类项目（faway_mes）对照
**结论概要**: 文档覆盖率广，但**结构、质量、可维护性**普遍达不到工程级标准；存在**指向不存在的总览文档**、**与代码技术栈不一致**、**多年沿用旧项目模板未清理**等系统性问题。

## 2. 文档结构共性问题

每个模块文档几乎都是同一个模板：

```
1. 模块概述
   1.1 功能定位
   1.2 核心功能
2. 页面清单
3. UI 设计规范
   3.1 页面基本结构     <- 通常写 "同 MES 模块标准布局"，没有内容
   3.2 状态映射         <- 通常是状态值→显示文本→颜色表
4. 业务流程            <- **文字流**，不是图
5. 数据模型            <- **字段列表**，没有关联、没有 ER
6. API 接口            <- **路由列表**，没有请求/响应 schema
7. 关联文档
```

### 2.1 缺失的章节（应统一补充）

| 章节 | 现状 | 影响 |
|------|------|------|
| **依赖与被依赖** | ❌ 完全缺失 | 不知道改一个模块影响哪些其他模块 |
| **角色与权限矩阵** | ❌ 完全缺失 | 谁能在什么页面做什么不清晰 |
| **状态机** | 🟡 只有状态值列表 | 没有转移条件、守卫、副作用 |
| **业务流程图（BPMN/PlantUML）** | ❌ 文字流 | 复杂分支难以表达 |
| **ER 图** | ❌ 完全缺失 | 表关系只能猜 |
| **时序图** | ❌ 完全缺失 | 异步流程、并发问题无法说清 |
| **API 请求/响应 schema** | 🟡 只有路由 | 前端对接要去看代码 |
| **错误码与失败语义** | ❌ 完全缺失 | 客户端只能靠试 |
| **性能/可用性目标** | ❌ 完全缺失 | 不知道优化到什么程度算合格 |
| **事件/消息流** | ❌ 完全缺失 | 集成接口怎么连不清 |
| **数据生命周期（归档/清理）** | ❌ 完全缺失 | 历史数据怎么处理不明 |
| **国际化/多语言** | ❌ 完全缺失 | 字典表怎么建不知道 |
| **兼容性/版本管理** | ❌ 完全缺失 | API 改了前端会不会挂 |
| **安全方案（认证/授权/审计）** | ❌ 完全缺失 | 只有 `sys_audit` 一个表，无明确策略 |
| **可观测性（日志/指标/追踪）** | ❌ 完全缺失 | 故障怎么定位 |
| **边界条件与异常处理** | ❌ 完全缺失 | 数据为空/超限/并发怎么处理 |
| **版本历史** | ❌ 部分有但很少更新 | 改了什么都不留痕 |

### 2.2 与实际代码/技术栈的偏差

| 文档 | 文档描述 | 实际代码 | 评估 |
|------|----------|----------|------|
| BPM 模块 | Flowable + MyBatis-Plus + MySQL 8.0 + Spring Security 6.x | Go + Gin + GORM + PostgreSQL 18（虽然是 Flowable 但持久化层不同）| 🔴 **严重滞后** |
| 设备管理（SQL 部分）| MySQL 8.0 DDL 语法（`datetime DEFAULT CURRENT_TIMESTAMP`、字符集 `utf8mb4`）| PostgreSQL 18（`timestamp with time zone DEFAULT CURRENT_TIMESTAMP`）| 🔴 **SQL 不可用** |
| 设备管理（子模块名）| `win-module-wms-biz` | Go 模块 `mom-server/internal/handler/equipment` | 🔴 **结构错位** |
| WMS 仓储（大量子模块）| `win-module-wms-api` / `win-module-wms-biz` | Go 模块 `mom-server/internal/handler/wms` | 🔴 **结构错位** |
| ARCHITECTURE.md | React + Go | **Vue 3** + Go | 🟡 滞后 |
| 主数据、BOM 引用 | Spring/Java 风格术语 | GORM/AutoMigrate 风格 | 🟡 部分 |

### 2.3 文档命名与组织问题

- **所有模块都引用 `MOM3.0_主设计文档.md`，但此文件不存在** — 是「幻影依赖」，给团队制造假象
- **`MOM3.0_UI设计规范.md` 不存在**，但所有 UI 章节都说「同 X 模块标准布局」
- **没有 `archive/` 目录** — 旧版文档散落各处，容易和活跃文档混淆
- **没有 CODEMAP**（代码索引）— faway_mes 那边 53KB 的 CODEMAP.md 是 best practice
- **没有 DOCUMENTATION_GUIDE**（文档维护规约）— 团队各自写各自的
- **docx 文件夹不规范** — `MOM3.0_完整系统设计规范 V1.0.docx` 是 Word 格式，不便 review 和 diff
- **目录分层不清晰** — 都堆在 `docs/` 根目录，没有按业务域或子系统分类

## 3. 现状评估总结

### 3.1 优点
- ✅ DEVELOPMENT_STATUS.md（基于 API 测试的覆盖率）— 这就是 best practice
- ✅ TODO.md（P0/P1/P2 + 文件定位）— best practice
- ✅ SAP Gap Analysis（整改计划 + 优先级 + 工作量）— best practice
- ✅ 状态映射表（每个模块都有）— 至少把状态值→显示文本说清了
- ✅ 文档数量充足（30 个 markdown，约 30K 行）
- ✅ 实际代码 + 数据库覆盖率 ~90%
- ✅ 16 个业务模块全覆盖
- ✅ ARCHITECTURE.md（虽然小）是 Context Hub 起点

### 3.2 缺点
- ❌ 「主设计文档」是幻影（所有模块都引用它）
- ❌ 文档结构 90% 雷同，缺乏差异化（核心模块如 ASP/追溯/报表只 100-200 行，不够）
- ❌ 没有图（流程图、状态机图、ER图、时序图、架构图统统没有）
- ❌ 没有角色权限矩阵
- ❌ 没有 SLA/性能目标
- ❌ 没有错误码规范
- ❌ 没有事件流/消息流
- ❌ 没有 API 详细规范（OpenAPI）
- ❌ 多个文档技术栈描述滞后（BPM/MySQL DDL/Java 目录）
- ❌ 没有 CODEMAP（代码索引）
- ❌ 没有 DOCUMENTATION_GUIDE（文档维护规约）
- ❌ 没有 DESIGN_CODE_GAP_ANALYSIS（设计 vs 代码偏差跟踪）
- ❌ 没有 archive 策略（废弃文档散落各处）
- ❌ 字段命名和数据类型在文档与代码之间不一致
- ❌ 没有版本历史（改了什么都不留痕）
- ❌ docx 设计规范与 markdown 设计文档并存，容易过期

### 3.3 整体评分（10 分制）

| 维度 | 分数 | 说明 |
|------|------|------|
| **覆盖广度** | 8 | 16 模块全覆盖 |
| **结构规范** | 4 | 雷同模板，缺 10+ 关键章节 |
| **图表表达** | 1 | 几乎没有图，全是文字 |
| **与代码同步** | 3 | 多个文档技术栈描述滞后 |
| **可维护性** | 3 | 没有维护规约、archive、版本历史 |
| **总览性** | 2 | 主设计文档缺失、架构图缺失 |
| **API 文档化** | 3 | 只有路由，没有 schema |
| **数据建模文档** | 2 | 只有字段，没有关系 |
| **非功能需求** | 1 | 完全缺失 |
| **总体** | **3 / 10** | 文档量够，但工程级质量欠缺 |
